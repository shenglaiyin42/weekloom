# Weekloom 产品基线 v0.1

状态：已确认
基线日期：2026-08-16

本文档是 Weekloom 当前产品设计与开发的统一基础。后续出现新决定时，更新对应章节和版本记录，不重新从最初的头脑风暴开始。

## 1. 产品定位

**产品名称：** Weekloom
**中文名称：** 周织
**标语：** 把项目织进每一周。

Weekloom 是一套个人使用的每周计划、GTD、项目推进和每周复盘系统。它将纸笔规划方式数字化，帮助用户把长期项目转化为每周能够实际执行的行动。

Weekloom 首先服务于用户本人。首版不以通用商业效率产品为目标，设计重点是简单、可靠、可持续使用，并能逐步演进。

## 2. 核心目标

Weekloom 帮助用户：

- 同时管理工作、个人项目、个人生活和兴趣学习。
- 把长期项目拆成本周可执行的行动。
- 明确本周真正承诺完成的事情。
- 快速收集临时出现的想法和待办。
- 识别长期未推进、反复延期或受到阻碍的项目。
- 保留每周计划和复盘历史。
- 通过 GitHub 获得版本管理、备份和跨电脑同步。
- 通过 Excel 查看项目进度和长期趋势。
- 让 Codex 读取结构化数据、协助复盘并提出建议。

## 3. 核心使用闭环

```text
随时收集
  → 每周选择
  → 拆解行动
  → 日常更新
  → 每周复盘
  → 调整项目下一步
```

1. 临时事项先进入 Inbox。
2. 每周规划时整理 Inbox。
3. 从活跃项目中选择本周要推进的内容。
4. 把项目转化为明确的下一步行动。
5. 日常更新行动状态。
6. 周末完成复盘。
7. 根据复盘调整项目状态和下周重点。

## 4. 项目与行动

项目代表一个需要多个步骤才能完成的结果，例如“发布 Weekloom MVP”。行动则必须是能够直接执行的具体动作，例如“确定 Weekloom 的 JSON 字段”。

每个活跃项目应尽量保持至少一个明确的下一步行动。

## 5. MVP 范围

首版支持：

- Inbox 快速收集。
- 创建和编辑项目。
- 设置项目状态和下一步行动。
- 创建本周计划并将行动加入本周。
- 设置类别、优先级和本周角色。
- 更新行动完成状态。
- 填写每周复盘。
- 查看基础项目汇总。
- 识别停滞、延期和受阻项目。
- 保存结构化数据。
- 生成基础 Excel 仪表盘。
- 通过 GitHub 保存和同步数据。

首版暂不追求：

- 团队协作和复杂权限。
- 完整日历系统。
- 复杂任务依赖和高度自定义工作流。
- 移动端原生应用。
- 强制依赖 OpenAI API。
- 高度自动化。

## 6. 每周事项分类

类别表示事项所属的生活领域。首版采用：

1. 工作
2. 个人项目
3. 个人生活
4. 兴趣与学习

健康、家庭、社交和财务等内容暂时归入“个人生活”。经过数周实际使用后，再决定是否拆分。

## 7. 优先级

“紧急”属于优先级，不属于事项类别。首版采用：

1. 紧急
2. 高
3. 普通
4. 低

类别与优先级相互独立，例如一项行动可以同时属于“工作”和“紧急”。

## 8. 本周角色

本周角色表示事项在当前一周中的承诺程度：

1. **本周重点：** 本周真正承诺完成或明显推进的事项。
2. **一般计划：** 希望本周完成，但不是最核心的事项。
3. **候选事项：** 有额外时间时再做。
4. **例行事项：** 每周或定期重复的行动。

建议每周控制在三个核心成果、三至五个重点项目，每个重点项目安排一至三个本周行动。其他事项可以记录，但不全部视为本周承诺。

## 9. 行动状态

- `todo`：待办
- `doing`：进行中
- `done`：已完成
- `dropped`：本次放弃

未完成行动不会无条件自动滚动到下一周。新一周开始时需要重新确认，避免积压事项无限累积。

## 10. 项目状态

- `active`：正在推进
- `waiting`：等待外部条件
- `paused`：主动暂停
- `completed`：已经完成
- `archived`：已经归档

系统需要识别：

- 活跃但没有下一步行动的项目。
- 连续多周没有推进的项目。
- 长期处于等待状态的项目。
- 行动反复延期的项目。
- 明确受到阻碍的项目。

## 11. 可选标签

标签用于补充类别，但不是必填项。可能的标签包括 `电脑`、`外出`、`电话`、`等待他人`、`深度工作`、`30分钟内`、`家里` 和 `财务`。

首版不建立复杂的标签管理功能，只保留简单扩展能力。

## 12. 本地 App

本地网页 App 是主要的数据输入和日常操作界面，运行在浏览器 `localhost` 中，提供：

- 快速收集 Inbox。
- 创建和编辑项目。
- 制定本周计划。
- 查看本周重点。
- 更新行动状态。
- 填写每周复盘。
- 查看受阻和停滞项目。
- 保存本地数据。
- 查看 GitHub 同步状态。
- 创建 Codex 复盘请求。

首页默认聚焦当前一周，展示本周三个核心成果、本周重点行动、一般计划、受阻项目、停滞项目、快速收集入口和周复盘入口。

本地保存与 GitHub 同步必须分开。应用应显示“已保存到本地”“有尚未同步的更改”“已同步到 GitHub”或“存在同步冲突”等状态，日常记录不因离线而受阻。

## 13. 数据架构

Git 友好的结构化数据是唯一真实数据源：

- JSON 保存项目、行动、周计划、复盘和请求。
- 必要时生成 CSV 供表格工具读取。
- XLSX 是生成的仪表盘和导出物，不作为核心数据源。
- 浏览器 `localStorage` 不作为主要存储。
- 每个项目和每一周分别保存为独立文件，减少同步冲突。

## 14. Excel

Excel 是查看、分析和导出的工具，不是主要录入界面。首版建议包含：

- `Dashboard`
- `Projects`
- `Weekly Log`
- `Actions`

仪表盘优先展示异常和决策信息，包括项目状态、每周完成趋势、核心成果完成情况、停滞或受阻项目、没有下一步行动的项目、反复延期的行动以及每周承诺是否过多。

日常编辑主要在 App 中完成，避免 App 与 Excel 双向修改数据造成冲突。

## 15. GitHub 与隐私

公开仓库 `shenglaiyin42/weekloom` 只保存应用代码、文档、空白模板、数据格式和匿名示例数据。

真实工作内容、个人计划和周复盘不进入公开仓库。推荐将真实数据保存在独立的 private repository 或仓库外部的私人数据目录中，并通过 `WEEKLOOM_DATA_DIR` 连接。

系统应支持本地离线工作，联网后再同步。换机时可克隆代码和私人数据仓库、完成身份验证、启动本地应用并重新生成 Excel。

## 16. Codex 复盘

MVP 不依赖 OpenAI API，也不在浏览器前端保存 API key。首版使用文件请求工作流：

1. App 创建请求到 `requests/pending/`。
2. Codex 读取本周数据和请求。
3. Codex 总结本周、识别问题并建议下周重点。
4. 必要时更新结构化数据或导出物。
5. 请求归档到 `requests/completed/`。

复盘重点包括本周成果、未完成原因、长期停滞、反复延期、缺少下一步的项目、下周聚焦事项，以及应该暂停、删除或降低优先级的内容。

## 17. 开发顺序

1. 初始化仓库并保存本基线。
2. 确定公开代码与私人数据的本地连接方式。
3. 定义 Project、Action、Week、Inbox Item 和 Review 数据模型。
4. 创建匿名示例数据。
5. 完成“创建项目 → 加入本周 → 完成行动 → 周复盘”的最小纵向流程。
6. 开发第一版本地 App。
7. 根据真实数据生成第一版 Excel。
8. 加入停滞、阻塞和延期检测。
9. 加入 GitHub 同步。
10. 加入 Codex 文件复盘工作流。
11. 实际使用数周后再调整分类、字段和界面。

## 18. 尚待决定

- 周复盘模板的具体问题。
- 私人数据仓库的创建与连接方式。
- GitHub 冲突处理界面。
- Excel 的具体图表和视觉风格。
- App 技术栈。
- 例行事项的重复规则。
- 截止日期和日历的首版支持程度。
